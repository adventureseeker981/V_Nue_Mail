# Database Normalization — V_Nue Mail

**Project:** V_Nue Mail  
**Database:** PostgreSQL  
**Scope:** User accounts and incoming email messages  
**Source schema:** `setup_db.sql`

## 1. Overview

V_Nue Mail is a mail system with a Rust SMTP server, PostgreSQL storage, and a Node.js/Express API. The database setup currently defines two tables: `users` and `messages`.

This document explains the current schema, identifies its normalization issue, and presents a normalized relational design for message recipients.

## 2. Current database structure

### `users`

| Column | Data type | Constraint / purpose |
|---|---|---|
| `id` | UUID | Primary key; generated by `gen_random_uuid()` |
| `email` | TEXT | UNIQUE, NOT NULL |
| `password_hash` | TEXT | NOT NULL |
| `display_name` | TEXT | Optional |
| `created_at` | TIMESTAMPTZ | Defaults to `NOW()` |

### `messages`

| Column | Data type | Constraint / purpose |
|---|---|---|
| `id` | UUID | Primary key; generated by `gen_random_uuid()` |
| `sender` | TEXT | NOT NULL |
| `recipient` | TEXT[] | NOT NULL; currently stores multiple recipients as an array |
| `subject` | TEXT | Defaults to `'(NO SUBJECT)'` |
| `body` | TEXT | Optional |
| `raw_headers` | TEXT | Optional; preserves raw SMTP headers |
| `status` | TEXT | Defaults to `'unread'` |
| `created_at` | TIMESTAMPTZ | Defaults to `NOW()` |

The current SQL also creates indexes on `messages.recipient`, `messages.status`, and `messages.created_at`.

## 3. Unnormalized / current recipient representation

A message may have more than one recipient. The current schema stores them together in one `TEXT[]` value, for example:

| id | sender | recipient |
|---|---|---|
| M1 | alice@example.com | `{bob@example.com, carol@example.com}` |

This is convenient for storage, but the recipient column contains a collection of values rather than one atomic value per row. That makes recipient-level operations and constraints less relational.

## 4. First Normal Form (1NF)

A relation is in 1NF when each field contains a single atomic value and there are no repeating groups.

**Change:** move recipients into a separate table, with one row per recipient.

### `messages` (1NF design)

| id (PK) | sender | subject | body | raw_headers | status | created_at |
|---|---|---|---|---|---|---|
| M1 | alice@example.com | Hello | ... | ... | unread | timestamp |

### `message_recipients` (1NF design)

| message_id (FK) | recipient_email |
|---|---|
| M1 | bob@example.com |
| M1 | carol@example.com |

The pair `(message_id, recipient_email)` can be used as a composite primary key if duplicate recipient addresses within the same message are not allowed.

## 5. Second Normal Form (2NF)

A relation is in 2NF when it is in 1NF and every non-key attribute depends on the whole candidate key.

In `message_recipients`, the proposed composite key is `(message_id, recipient_email)`. There are no additional non-key attributes in this relation, so there is no partial dependency to remove.

In `messages`, `id` is a single-column primary key. All message attributes describe that message and depend on `id`.

In `users`, `id` is a single-column primary key. The account attributes depend on `id`; `email` is also a candidate key because it has a UNIQUE constraint.

## 6. Third Normal Form (3NF)

A relation is in 3NF when it is in 2NF and non-key attributes do not depend transitively on a key through another non-key attribute.

The proposed design keeps message data in `messages`, recipient rows in `message_recipients`, and account data in `users`. No additional transitive dependency is indicated by the current SQL definitions.

## 7. Proposed normalized schema

```sql
CREATE TABLE message_recipients (
    message_id UUID NOT NULL
        REFERENCES messages(id) ON DELETE CASCADE,
    recipient_email TEXT NOT NULL,
    PRIMARY KEY (message_id, recipient_email)
);
```

For this design, `messages.recipient` should be removed after the application code has been updated to insert and read rows from `message_recipients`. Do not run this change against a database with existing data until the data has been migrated.

## 8. Entity relationships

- One `messages` row can have many `message_recipients` rows.
- Each `message_recipients` row belongs to exactly one message.
- `users` represents registered accounts.
- The current schema does not declare a foreign key between `users` and `messages`: `sender` and `recipient` are email-address text values, and SMTP mail can involve addresses that are not registered V_Nue Mail users.

See `er_diagram.png` for the proposed normalized relational design.

## 9. Benefits

1. Each recipient address is stored as an individual value.
2. Recipient-level searching and filtering become easier.
3. A foreign key ensures recipient rows cannot refer to a non-existent message.
4. `ON DELETE CASCADE` prevents orphaned recipient rows when a message is deleted.
5. The design avoids storing a repeating list in one database column.

## 10. Implementation note

The repository's current `setup_db.sql` still defines `messages.recipient` as `TEXT[]`. The `message_recipients` table above is a **proposed normalization improvement**, not a description of the currently deployed schema. The Rust SMTP ingestion code and API queries must be updated together before adopting it.

This document is based on the repository's `setup_db.sql` and README. It does not assume that application-level migration has already happened.
